# Spec: gateway database migrations

Status: approved, 2026-10-10. Decisions marked **(owner)**.

## Why
The gateway's schema is `create_all` plus ~60 idempotent `ALTER … IF NOT EXISTS` run at
startup. Measured on 2026-10-10: a database created today and one upgraded over months
differ (a missing FK on flows.notify_connection_id, TEXT vs VARCHAR on
flows.notify_emails, server defaults present only on the upgraded one). Only additive
changes are possible, the database has no version, the "every new column needs its
ALTER" rule is manual, and the migration runs inside the app during a rolling update.

## Decisions
- **(owner) Alembic.** Migration files in `gateway/migrations/`, autogenerated from the
  models and reviewed. The models are the single source of truth (partial indexes and
  server defaults declared there).
- **(owner) A separate step in production**: `python -m app.db.migra` — a Helm Job before
  install/upgrade, a one-shot compose service. The gateway checks the revision and refuses
  to start if the database is behind. In development (`DB__AUTO_MIGRATE=true`) it migrates
  at startup, under the advisory lock.
- **(owner) Forward only.** Fixes are new migrations; backups for rollback. Expand/contract:
  a migration must work with the previous release's code still running.
- Baseline `0001` = today's models. A pre-Alembic database (tables, no alembic_version) is
  adopted: the frozen legacy ALTER list brings it to the last pre-Alembic state, a
  realignment fixes the measured drift, it is stamped `0001`, then the live schema is
  compared with the models — any difference stops the step.

## Acceptance
1. A fresh database migrated to head equals the models (Alembic compare: empty).
2. A real pre-Alembic database (the dev one's schema, as a fixture) is adopted and then
   equals the models; running the step twice changes nothing.
3. A model changed without a migration fails a test.
4. The gateway with AUTO_MIGRATE off refuses to start on a database behind, with a clear
   message; with it on, it migrates.
5. Helm chart: a pre-install/pre-upgrade Job (lint + template); compose: a `migrate` service.
6. Full regression green; docs: how to add a migration, the expand/contract rules.
